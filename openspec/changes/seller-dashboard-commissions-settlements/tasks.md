## 3. Seller earnings (extend payment approval, idempotent, review-flagged fallback)

- [x] 3.1 Write `supabase/migrations/0051_seller_earnings_schema.sql`: `seller_earnings` table (`id`, `seller_id`, `order_id`, `payment_id`, `gross_amount`, `commission_rate`, `commission_amount`, `seller_net_amount`, `status` check (`PENDING`,`AVAILABLE`,`IN_SETTLEMENT`,`SETTLED`,`REVERSED`), `needs_commission_review boolean default false`, `reversal_of_earning_id`, `backfilled boolean default false`, timestamps), RLS (seller reads own via `seller_id` match; admin reads all; no client write policy). - [x] 3.3 Write `supabase/migrations/0053_seller_earnings_backfill.sql`: one-time backfill of `seller_earnings` for pre-existing `APPROVED` payments lacking one, using the currently-active rule (or the review-flagged fallback), each row marked `backfilled = true`.

## 7. Verification (authorization, idempotency, race conditions, segment/commission changes, historical correctness)

**Environment note**: this sandbox has no local Postgres/Supabase (no Docker daemon access, no `supabase` CLI, no `psql`), so 7.1–7.2 and 7.4–7.10 below could NOT be executed against a real database in this session. What *was* done instead, as the best available substitute:
- Every new migration (`0048`–`0057`) was parsed with `libpg-query` (the real Postgres grammar, via a throwaway Node script) — all 10 files parse as valid SQL at the statement level.
- Every function body was manually re-read end to end against the design's invariants. This caught and fixed two real bugs before they'd have surfaced at runtime: (a) the original `unique (payment_id, seller_id)` on `seller_earnings` would have made `reverse_seller_earning`'s compensating insert fail, since a reversal intentionally reuses the same `payment_id`/`seller_id` — fixed with a partial unique index scoped to `reversal_of_earning_id is null`, plus a second partial index capping one reversal per original; (b) a single-column `unique (seller_earning_id)` on `settlement_items` would have blocked a cancelled settlement's earning from ever being claimed by a later settlement — removed, leaving only the per-settlement compound unique.
- The full Angular app (`ng build`, both `development` and the default production config) compiles clean, including Angular's template type-checker — this caught and fixed three real template errors (`min`/`max`/`disabled` bindings alongside `[formField]` in the new seller-segment/commission-rule forms).
- `npm test` still passes everything it passed before (the one pre-existing failure, `app.spec.ts`'s stale "Hello" title check, is untouched by this change and fails identically on `master`).

None of that is a substitute for 7.1–7.2/7.4–7.10 actually running against Postgres. **Before merging, run this change's migrations against a local or staging Supabase project and execute those items for real** — they are left unchecked below deliberately, not because the work was skipped, but because it could not be completed in this environment.

## 8. Post-implementation fixes (found during live QA against the real Supabase project)

- [x] 8.1 `backoffice-layout.component.ts`'s hardcoded `adminNavItems`/`sellerNavItems` arrays were never updated — every new page in this change had a working route but no sidebar entry. Added "Segmentos de Vendedor", "Comisiones", "Comisiones Pendientes" (with a live badge count) to the admin list; "Panel financiero" and "Liquidaciones" to the seller list.
- [x] 8.2 `navItems` defaulted to the admin list whenever `role !== 'SELLER'` — including the `undefined` state before the user loads (SSR has no session; client fetch is still in flight on reload). A signed-in seller briefly saw the admin sidebar on every reload. Fixed to branch explicitly per role (`SELLER`/`ADMIN`/`SUPER_ADMIN`) and return `[]` otherwise, never falling through to admin.
- [x] 8.3 The segment `<select>` in `seller-review.component.ts` (and the same pattern copied into `settlement-form.component.ts`'s seller picker and the seller dashboard's period selector) bound `[value]` on the `<select>` itself. Confirmed via live network inspection that `assign_seller_segment` was persisting correctly and `seller_segments` was loading correctly — the assigned segment just never displayed as selected. Root cause: Angular applies a `<select>`'s own property bindings before its `@for`-generated `<option>` children exist in the DOM, so the browser's native "select the matching option" logic ran before there was anything to match, and never re-ran afterward. Fixed all three by moving the binding onto each `<option>`'s own `[selected]` property instead, which has no such ordering dependency.
