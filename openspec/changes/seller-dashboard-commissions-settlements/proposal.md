## Why

Sellers can already see their orders (`seller-order-fulfillment`) but have no financial picture at all: no gross sales, no visibility into what the marketplace commission actually is, no idea how much has been settled versus how much is still owed to them. Today nothing in the schema even knows what a seller's commission rate *is* — there is no segment, no commission rule, no earning, no settlement. Every payment that reaches `APPROVED` (`wompi-payment-integration`) currently has no financial consequence for the seller beyond the read-only order it's already attached to. This change adds the missing financial layer — segment-based commission configuration, a frozen-at-the-time earning per seller per paid order, admin-run settlements, and the seller dashboard that reads all of it — without touching the existing checkout/payment state machine.

## What Changes

- Add `seller_segments` (catalog: `DISTRIBUTOR`, `LABORATORY`, `LIVESTOCK_COMPANY`, admin-managed, soft-deactivated only) and `seller_profiles.segment_id` (nullable FK) as the single normalized source of a seller's commercial segment — no code path re-reads `seller_onboarding_responses` to determine commission.
- Add `seller_segment_commission_rules` (segment + `commission_rate` as a `0–100` percentage + `effective_from`/`effective_until`, admin-managed) with a non-overlap constraint per segment so at most one rule is active for a given segment at a given instant, and a `get_current_commission_rate(segment_id, at timestamptz)` lookup function.
- Extend `apply_payment_approved` (owned by `wompi-payment-integration`) with an additive block — same "cross-change extension point" pattern `seller-order-fulfillment` already used on this function — that creates one `seller_earnings` row per distinct seller in the order, resolving each seller's rate via `get_current_commission_rate` at approval time and freezing `commission_rate`/`commission_amount`/`seller_net_amount` onto the row permanently. A unique constraint on `(payment_id, seller_id)` makes this idempotent under duplicate/retried webhooks, matching the existing `webhook_events` dedupe strategy.
- Add `seller_earnings` states (`PENDING`, `AVAILABLE`, `IN_SETTLEMENT`, `SETTLED`, `REVERSED`) and a reversal path: a `REVERSED` earning is never deleted or edited in place — a compensating negative-amount row is inserted instead, preserving the original.
- Add `settlements` + `settlement_items` (admin-only writes): an admin selects `AVAILABLE` earnings for a seller, creates a `DRAFT`/`PENDING` settlement, and marks it `PAID` — which atomically flips its earnings to `SETTLED`. A partial unique index / row-locking `FOR UPDATE SKIP LOCKED` claim on `seller_earnings.status = 'AVAILABLE'` prevents the same earning from ever landing in two concurrent settlements.
- Add `seller.segment_id` change and commission-rule change audit trail (`segment_change_log` / reusing the existing generic audit pattern from `protect_seller_profile_status`-style triggers) so segment/commission changes are attributable, and add a trigger blocking a `SELLER` from writing their own `segment_id` (mirrors `protect_seller_profile_status`, 0023).
- Add a `get_seller_dashboard_summary(date_from, date_to)` security-definer RPC (seller id resolved from `auth.uid()`, never client-supplied — same pattern as `get_seller_orders`) returning gross sales, order count, doses sold, average order value, total collected, commission, net, pending-settlement amount, and settled amount for the calling seller only.
- Add the seller dashboard UI at `/seller/dashboard` (summary cards, period selector, recent orders, segment/commission display, settlements history + detail) and an admin "Seller Segments" section (`/admin/seller-segments`) for segment + commission-rule CRUD, plus a settlement creation/processing screen under `/admin/settlements`.
- Doses-sold and gross-sales figures explicitly exclude order items belonging to orders that never reached a payment-approved state, and are computed from `order_items` scoped by `seller_id` and joined through `seller_earnings`, never directly summed from `orders.total` (which is a whole-order, potentially multi-seller figure).
- **Scope decision**: this marketplace's payment/order schema has no `REFUNDED` status today (`payments.status` and `orders.status` check constraints stop at `DECLINED`/`CANCELLED`/`EXPIRED` — confirmed by inspecting `0031`/`0032`/`0035`). Building a full Wompi-refund-triggered automatic reversal is out of scope for this change; it ships the `REVERSED` earning state and an admin-triggered manual reversal action (with required reason) so the data model and audit trail are ready, but the trigger is a human action, not an automatic webhook-driven one. Automatic refund-driven reversal is deferred to a future change once refunds exist as a first-class order/payment status.
- **BREAKING**: none to existing behavior. All new tables are additive; `apply_payment_approved`'s existing checkout/payment/order transitions and `seller-order-fulfillment`'s existing extension block are unchanged — this only appends a further additive block, same as 0045 did.

## Capabilities

### New Capabilities
- `seller-segments`: segment catalog (code/name/description/active), admin CRUD, `seller_profiles.segment_id` assignment and reassignment, audit of segment changes, seller-facing read of their own current segment.
- `commission-rules`: time-versioned commission rate per segment (percentage convention, `effective_from`/`effective_until`, no overlaps), admin CRUD including "change effective a future date" without touching history, current-rate resolution function, seller-facing read of their own current rate.
- `seller-earnings`: one frozen-commission earning row per seller per approved payment, created only on genuine payment approval (never on order creation alone), idempotent under duplicate webhooks, state machine (`PENDING → AVAILABLE → IN_SETTLEMENT → SETTLED`, plus `REVERSED`), manual admin-triggered reversal with audit trail.
- `seller-settlements`: admin-created settlements grouping `AVAILABLE` earnings for one seller into `DRAFT/PENDING/PROCESSING/PAID/CANCELLED/FAILED` records with `settlement_items` detail, race-safe exclusive claiming of earnings, settlement history and detail readable by the owning seller (read-only) and admins (read/write).
- `seller-dashboard`: seller-facing `/seller/dashboard` — sales summary with selectable period (today/7d/30d/this month/last month/this year/custom), doses sold, financial cards (collected, commission, net, pending settlement, settled), recent orders, segment + commission display (read-only), settlement history access — backed by a single server-side aggregation RPC scoped to the caller's own seller id.

### Modified Capabilities
(none — `wompi-payment-integration`'s existing requirements for `apply_payment_approved` are unchanged; this change appends a further additive extension block to that function, the same pattern `seller-order-fulfillment` already established, rather than altering any of its stated behavior. `seller-order-fulfillment` and `seller-tenant-identity` are read from, not modified.)

## Impact

- **Affected code**: new `supabase/migrations/0048_*` onward (segments, commission rules, earnings, settlements, extended `apply_payment_approved`, dashboard RPC, RLS, triggers); new `supabase/functions/seller-dashboard` (or a security-definer RPC called directly, see design.md), new `supabase/functions/admin-settlements` (create/process/pay), new `supabase/functions/admin-seller-segments` (or direct table access under RLS if simple enough — see design.md); new `src/app/features/seller/dashboard/*`, `src/app/features/admin/seller-segments/*`, `src/app/features/admin/settlements/*`; `src/app/features/seller/seller-routes.ts` and `src/app/features/backoffice/backoffice-routes.ts` (new routes); `src/app/shared/const/routes.ts` (new `RoutesApp` entries); new `core/services`/`core/models` for segments, commission rules, earnings, settlements, dashboard metrics; `src/app/app.routes.server.ts` (new `:id`-bearing routes, e.g. settlement detail).
- **Depends on**: `seller-tenant-identity` (`seller_profiles`), `wompi-payment-integration` (`payments`, `apply_payment_approved`), `seller-order-fulfillment` (`order_items.seller_id`, established multi-seller-per-order reality) — this change's migrations continue that numbering sequence and assume that schema exists.
- **Not in scope**: automatic refund-driven earning reversal (no `REFUNDED` payment/order status exists yet — see Scope decision above), payout execution/bank transfer integration (a settlement's `PAID` status only records that the admin executed payment elsewhere), multi-currency commission handling (marketplace is COP-only today), changing the buyer-facing checkout/order flow in any way.
